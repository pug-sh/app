# Theme engine, colour tokens and contrast

The colour rules that apply everywhere (`text-link` vs fills, `getSeriesColor` vs `getIndexedColor`, `themeRevisionAtom`, `bg-card`) are in CLAUDE.md under Colour. This file is for working on the tokens and the engine.

## Themes

Colours are data. A theme is a file in format v1 (`src/theme/format.ts`; JSON Schema in `schemas/theme/v1.json`, uploaded by hand to R2 at `/theme/v1.json`, since nothing in the repo publishes it). Pug is the built-in `pug` theme (`src/theme/presets/pug.ts`), alongside `pug-high-contrast` and `pug-colourblind`. The design and its reasoning are in `docs/superpowers/specs/2026-10-04-theme-engine-design.md` (local only; `docs/superpowers/` is gitignored).

- **A token registry computes what a theme leaves out** (`src/theme/registry.ts`, VSCode's colour-registry model). Roots (`background`, `primary`, the three semantic hues, `chart-1…5`, the fixed ramps) fall back to the built-in for the mode and contrast level. Every other token has a formula whose parameters are measured from Pug at load, so applying the formulas to Pug's roots reproduces Pug. `validate.test.ts` sweeps 432 partial themes across canvases and requires zero warnings; keep it that way when you touch a formula.
- **The values live in the presets, not `index.css`.** `bun run generate:themes` writes `src/theme/generated/builtin-themes.css` (tracked, imported by `index.css`) and the schema; `builtin-themes.test.ts` fails while either is stale. Edit a preset, regenerate, and the CSS diff is the review.
- **Pug must stay pixel-identical.** `src/theme/__fixtures__/` holds what `index.css`, `event-colors.ts`, `name-chip.tsx` and `retention-cohort.tsx` produced before the engine existed. Never regenerate them. A deliberate retune changes the preset and the golden expectation in the same commit, and says so.
- **Contrast is WCAG 2** (`src/lib/color/contrast.ts`), not APCA, because `apca-w3`'s licence restricts use. Standard floors are Pug's own ratio less 10%, capped at 7:1 (4.5:1 for name chips), pinned as `FLOORS` in `validate.ts` (`measureFloors` regenerates them), except text on a filled control, a flat 4.5:1. High contrast validates at the spec's APCA levels in WCAG terms (12:1 body, 7:1 secondary, 4.5:1 faint, 7:1 on fills, 3:1 for lines) and never below a standard floor; the registry solves its inks to the higher of 115% of Pug's ratio and 13 / 8 / 4.8, headroom over those floors, so it reads visibly stronger. A **surface** (anything text is drawn on, `SURFACES` in `tokens.ts`) must be opaque: contrast treats grounds as solid, so the parser refuses a see-through one. Measuring with APCA offline while tuning Pug is still right; see Dark mode below.
- **Event colours** live in `theme/data-palette.ts` as 20 groups with anchors; outcome crossovers sit in `failure`/`success`, so one anchor remaps every red/green pair. `lib/event-colors.ts` is only the lookup. A theme's own breakdown (categorical) colours are used exactly; left out, Pug's are fitted to the canvas. `adapt` fits event colours only, through `theme/fit.ts`, which reproduces Pug's series palette exactly on Pug's canvas and moves with any other.
- **Runtime:** `themeModeAtom` (`pug:theme`, values unchanged), `themeSelectionAtom` (one theme per mode), `autoContrastAtom` (OS `prefers-contrast: more` → Pug High Contrast), `installedThemesAtom` (≤ 20, stored as original text and re-parsed on load). Built-ins apply through `data-theme` and the generated CSS; installed themes as inline variables on `<html>` (`theme/apply.ts`). `index.html` paints from `pug:theme-paint` before React; keep it in step with `theme/paint-cache.ts` (`paint-script.test.ts` runs the real script).
- **`resolvedThemeAtom` is only for code that genuinely branches on light vs dark**: checkout, the share-card plate, and the sign-in wall, which draws Pug's own palette for the mode (`pugDataPalette`), never the active theme's.
- **Sign-in pages stay Pug**: the generated `.auth-surface` blocks reset every token.
- **Known issues kept for identity**, each to be fixed as its own reviewed visual change: the light fit clips 27 palette colours per channel (no `fitChroma`), and the retention ramp is the same in both modes, so low cells glow on dark.

## Series colour fitting

The base hexes are mid-tones that don't all read against either canvas (the darkest vanish on dark, the palest on white), so `getSeriesColor` adapts them per theme. Hue is preserved, so semantic families and the failure-red / success-green crossovers stay meaningful. Tune the bands in `theme/fit.ts`; do **not** add per-mode hexes.

- **Dark** lifts toward light: `L' = 0.54 + 0.22·L`, chroma capped at `0.165`, then gamut-fitted.
- **Light** caps lightness *and* chroma: `L' = min(L, 0.52)`, `C' = min(C, 0.14)`. Pale hues darken to the 0.52 ceiling, the most vivid desaturate to the 0.14 ceiling so they don't shout against the near-grayscale UI, and hues already under both caps pass through unchanged. The light chroma cap sits below dark's `0.165` because mid-lightness colours on white read as more saturated than lifted ones on dark.
- It is JS-driven because these are inline styles and SVG fills, not CSS vars: App pushes the active theme's compiled palette via `setSeriesPalette` during render, so badges and charts re-colour on any theme change.
- **The dark lift must be gamut-fitted, and shallow.** `fitChroma` binary-searches chroma down until the colour fits sRGB, holding L and H. Without it `linearToByte` clamps each channel independently, which drops chroma *and* shifts hue while still returning a valid hex, so nothing downstream notices. That silent clipping turned every dark series colour pastel: blue `#2563eb` asked for C 0.16 at L 0.78, where sRGB holds only 0.109, and landed as periwinkle. Spend lift sparingly, because every point of it is chroma the hue can no longer hold (sRGB's ceiling falls away toward white, blue first), and a deep ground needs less lift anyway. The band deliberately lands a rung *below* body ink so data never out-shouts the type.
- **The choropleth reads `--chart-1`, not `--primary`** (`lib/maplibre.ts` → `dataHue`). They are the same colour in light, but `--primary` is a fill tuned to carry white text, so in dark it stays deep, and the map washes it over the canvas at opacities from 0.16, where a deep hue on a deep ground is mud.

## Dark mode contrast

Light is the reference mode and is considered finished; dark is solved *against* it. Temperature is unified: every neutral sits at hue `265` in both modes (a cool tint on surfaces, near-neutral ink). A token that reads bluer or grayer than its neighbours is a regression, not a style choice.

- **Compare the modes with APCA, never with WCAG.** WCAG is polarity-blind: at the same 9:1 body contrast in both modes, every dark ink tier sat 22–32 Lc below its light twin, and dark kept being reported as washed out. **But APCA parity is the ceiling, not the target.** Solved for it, dark read as *hot*: halation is a physical effect of emitted light that no contrast model captures, and it only happens in the reverse polarity. The shipped ladder sits two notches below parity, at roughly `78 → 70 → 63 → 51 → 35` Lc from hero numerals down to hint text. Anchor any retune against two poles rather than a ratio: the washed-out body measured 62, full parity with light is 83, and the comfortable landing is 70. Dark's WCAG numbers still look high (body ~10.8:1); that is normal for this polarity and not a reason to walk it down.
- **There is no display ink tier.** Size alone carries display type, in body ink. Holding large text below body ink made the most important number on an analytics dashboard its softest type; one tier above body ink was more than the system needed.
- **Saturation reads as heat, independently of brightness.** Cooling dark meant pulling *chroma* out of the accents (`--primary`, `--link`, the semantic text tier, the series band) as well as lightness out of the ink. A vivid hue on a dark ground is felt as glare at a lightness that measures identically to a muted one.
- **Ground depth is not the contrast lever; ink is.** APCA's black clamp floors the background's contribution below Y≈0.022, so once the canvas is genuinely dark, taking it deeper changes the required ink lightness by <0.005 L. Deepen the ground for *material* (it gives colour room), never as a fix for text that reads weak.
- **A filled button and coloured body text pull lightness in opposite directions.** Dark `--primary` and `--destructive` are deep and saturated so **white button text clears AA** (4.8 and 5.1:1); coloured text wants to be light to read on the dark canvas, and no single token satisfies both at AA. So `--link` is the blue used *as text* (`text-link`) and `--primary` stays the **fill**. Don't lift the fills to fix coloured text.
- **Semantic text (`--positive`/`--caution`/`--negative`) is held at low chroma in dark**, well below the fills. Against a near-grayscale UI a saturated hue shouts on *colour* alone, at any lightness: a KPI row of five red delta pills was the loudest thing on the page while measuring as ordinary secondary text. Lightness sets the rung; chroma sets the volume.
- **Chip ink (`--accent-foreground`/`--secondary-foreground`) must stay softer than `--foreground`.** Solved for a flat target ratio it lands *past* body ink, because the chip grounds are lighter than the canvas; cap it below body instead (validation rule V6; `capToBody` in the registry). `--sidebar-accent-foreground` is the deliberate exception: the active nav item sits *above* body ink in dark.
- **The surface ladder mirrors light's proportions, including the sidebar**: sidebar, canvas, card, popover, chips, hover. Canvas and card currently share one tone, an experiment in a flat plane with regions drawn by hairlines rather than elevation, marked in the preset. The elevated ladder put the canvas one light-sized step (0.017 L) above the sidebar; pulling that step wider is what made attention land on the sidebar in dark and not in light. Two floors: `--accent` must stay above `--popover` (menu-item hovers render on popovers), and `--sidebar-accent` must stay below `--card`, so the active nav pill can never outshine content. The active nav item is marked by its **ink**, not by a brighter fill.
- Still deferred, deliberately: `text-destructive` *text* on the dark canvas is sub-AA (the same fill-vs-text conflict). Use `--negative`, which is what it is for, and don't lighten `--destructive` itself.
- `--faint` is a decorative tier and sits below AA on its brightest ground in **both** modes (light ~3.2:1, dark ~4.2:1 on a popover). That is the established treatment, not a regression, but it is the tier that breaks first, so re-check it against `--popover` whenever the ladder moves. Everything above it clears AA on every ground it lands on; the tightest real floor is white on `--primary` at 4.8:1.
- `--border` is translucent so one token works on canvas, card and popover; call sites dim it further with `border-border/30..70`. `--input` cannot be translucent: every form control styles itself `dark:bg-input/30` (some `/50`, `/80`), and Tailwind's `/NN` modifier *multiplies* alpha, so the fill would disappear.
